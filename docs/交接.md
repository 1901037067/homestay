## 1. 这是什么

本科毕业设计：**民宿房源管理与分时预订系统**（防超卖 + 分时计费 + 营业日报表 + 按民宿隔离）。

- 仓库 `https://github.com/1901037067/homestay`，分支 `main`。**每个里程碑都要提交并推送**（用户的一贯要求）。
- 时间预算：约半年，实施计划里那张 8 周表是**依赖顺序**不是工期 —— 不要为了赶周次砍掉防超卖验证、压测数据、反向对照这类得分点。
- 选型标准（用户明确说过）：**论文可写 + 答辩能讲 + 有测试数据**。宁可用 MySQL 手写并发，也不让数据库框架代劳核心技术。
- 前端风格：**Apple HIG**，令牌在 `frontend/src/styles/tokens.css`，不要混进 Element 默认观感。

技术栈：JDK 17 + Spring Boot 3.2.12 + MyBatis-Plus 3.5.9 + Flyway 9.22.3 + MySQL 8（Docker）
+ Testcontainers 集成测试 + springdoc；前端 Vue 3 + Vite + Element Plus + ECharts + Vitest。

**当前进度**：W1–W8 全部完成，**十二轮外部审阅的修复全部落地**。
测试 **185 后端 + 9 前端全绿**（2026-10-30 实测）；覆盖率 行 87.9% / 分支 70.3%（JaCoCo）；
迁移 8 个；业务表 9 张 + 外键 10 条；页面 10 个；CI 四次绿。

## 2. 怎么跑（本机实测过的路径）

```bash
# 只起数据库
docker compose up -d                      # 容器 bnb-mysql，宿主端口 3306

# 后端（Git Bash 里 mvn 不在 PATH，用 IDEA 自带的）
JAVA_HOME="C:\Program Files\Eclipse Adoptium\jdk-17.0.20.101-hotspot" \
  "/e/02_software/05_programming/04_IntelliJ_IDEA/plugins/maven/lib/maven3/bin/mvn.cmd" -o spring-boot:run

# 全量测试 / 前端
mvn -o test
cd frontend && npm test -- --run && npm run build
```

- **Docker Desktop 默认不运行**，要先手动起 `C:\Program Files\Docker\Docker\Docker Desktop.exe`，约 20 秒后 `docker info` 才通。
- Maven 离线用 `-o`（settings.xml 已配阿里云 `mirrorOf=central`，本地库在 `E:/02_software/05_programming/maven_repository`）。
- **开发和容器不要同时跑**（都占 8080/5173）；切回开发先 `docker compose --profile app stop backend frontend`（mysql 留着）。
- 杀 `mvn spring-boot:run` 不会带走它的 java 子进程：`netstat -ano | grep :8080` 拿 PID 再 `Stop-Process -Id <pid> -Force`。

### CI（GitHub Actions，2026-10-30 起）

`.github/workflows/ci.yml`：push 到 main / PR / 手动触发，两个任务并行 ——
后端 `mvn -B test`（runner 自带 Docker，Testcontainers 直接可用）+ 前端 `npm ci && npm test && npm run build`。
README 顶部有徽章。仓库是 public，标准 runner 不限分钟数。
**权限只要只读**（`permissions: contents: read`），这个工作流不写仓库、不发评论、不改 status。
artifact 共三份：`surefire-reports`、`jacoco-and-bench`（覆盖率 HTML + `target/压测报告.md`）。

**实测**：后端 1m30s、前端 10s（冷跑与热跑同速 —— runner 到 Maven Central 的带宽把
"首次下载依赖"这件事抹平了，`cache: maven` 在这里几乎不省时间）。日志末行
`Tests run: 185, Failures: 0, Errors: 0, Skipped: 0` 已用 `gh run view --log` 读到过，
不是从绿勾推的。

**四条要记住的**：
- **CI 上不能带 `-o`**。本地离线靠的是阿里云镜像 + 已填满的本地仓库，runner 两样都没有。
  看到 CI 报"找不到符号"先查有没有手滑加上 `-o`。
- **时区不用在 workflow 里处理**。pom 的 surefire `argLine` 已钉 `-Duser.timezone=Asia/Shanghai`，
  测试容器又钉了 `--default-time-zone=+08:00`，runner 是 UTC 也漂不了。
- **别只凭绿勾下结论**，要看到 `Tests run: N` 那一行。artifact 与日志都要已认证身份才读得到，
  匿名 API 会 401 —— 本机已装 `gh`（`C:\Program Files\GitHub CLI\gh.exe`，已登录）。
- **`--no-transfer-progress` 会把 Maven 的 `Downloaded from central` 整类行隐掉**。
  想判断"有没有现下载依赖"，去 grep `setup-java` 步骤里的 `Cache hit for:`，别数下载行数（数出来是 0，会误判）。

**还没定的**：那四个压测/对照类（`ConcurrencyBench*`、`OversellWithoutLockIT`）目前也在 CI 里跑，
四次都绿。`OversellWithoutLockIT` 断言的是"**必须**出现超卖"，依赖竞态在共享 runner 上真交错起来。
现在的策略是继续观察，**确实抖了才**把它挪到 `workflow_dispatch` 单独一档 —— 别凭猜测预先阉割。

## 3. 核心口径（改代码前必读，都是被审阅一轮轮钉出来的）

**两条总纲**（实施计划 2.3）：
- **A**：`occupancy` 有一行 = 这段时间被占住；释放 = DELETE。所以报表读 `booking`/`bill`，**永远不读 `occupancy`**。
- **B**：退房不是删空，而是把 ROOM 行换成 CLEANING 行；**保洁点"清扫完成"才真正可售**（确认式闸门，不会到点自动放行）。

**防超卖**（论文第 4 章）：
- 半开区间 `[start, end)`；悲观锁 `SELECT ... FOR UPDATE` 锁房间行；**冲突检测必须是当前读** —— RR 下一致性读视图在事务第一条普通 SELECT 就建立了，而真实入口进内核前还要先查房间/房型/民宿，拿锁后的普通 SELECT 看不到别人刚提交的占用 → 超卖。反向对照 `OversellWithoutLockIT` 把这一句降级成普通 SELECT，实测 10/10 轮超卖。
- 统一加锁顺序：**房间行 → 订单行**。任何新写路径都不能反（幂等回放的只读探测因此刻意不加锁）。
- 冲突判定只在一处：`OccupancyMapper.lockOverlapping` 的三个 OR 分支（几何重叠 / 超时在住持续挡 / 待清扫持续挡）。`RoomMapper.findAvailable` 与前端 `utils/sellable.js` 是它的镜像，**改一处要同时改三处**（历史上漏过两次）。
- MyBatis 一级缓存作用域 = 一个事务 ≈ 一个 SqlSession：**加锁后再 `selectById` 会读回加锁前的旧对象**，所以锁查询一律返回整行（`select * ... for update`、`findByIdForUpdate`）。

**占用真相**：改变实际占用范围的动作（提前入住、加时、改期）**都要重跑冲突检测**。
提前入住会把 `block_start` 前扩，不检测就能把两个互不冲突的单叠到一起。

**幂等探测三态**（`BookingKernel.replayOf`）：`MISS` / `REPLAY` / `CONFLICT`。
同标识不同内容也是**命中**，必须在服务层就直接抛 `3005` —— 当成 `MISS` 继续往下走，
报错码会被更靠前的可售性判断抢掉（实测变成 `2003`）。规则同"占用真相"：**已经写进库的事实，
不能被"现在怎么样"覆盖**，无论答案是原单还是拒绝。

**清扫窗口**：被下一单挤时**截断**，挤到底长度是 0 但**仍要留一条零长 CLEANING 行**（日历块、"清扫完成"按钮、挡下一单的闸门都挂在它上面）。操作日志写**实际**分钟数，不照抄房型配置。

**账号编辑是"部分更新"，省略的字段一律保持原值**（第十二轮）：`enabled` 传 null 曾回落成"启用"，
于是调一次"改显示名"就把停用的账号悄悄放回来，还顺带绕过"不能停用自己 / 至少留一个店长"两道守卫。
密码一直是这么处理的（不传 = 不动），`enabled` 跟上。同一轮还补了：登录成功 `changeSessionId()`（会话固定）、
前端 `/users` 的 `meta.manager` 守卫 —— **后者只是体验层，真正的拒绝始终在 `requireManager()`**，
别把前端隐藏当成权限。

**计费**（论文第 5 章）：规则不叠加、决胜必须全序（priority → 房型级压民宿级 → id）；
起步价按入住时刻定价、超时段按各自起点定价；取整只发生在计费单元一级（HALF_UP 到分），
明细之和恒等于合计；**试算不落库，结算才落快照**（V7 把计费基准冻结到 `booking` 上，改房型不回溯旧单）。

**营业日切割**：`property.day_cut_time` **只收整点**（分钟级会让"归哪天"和"画第几格"对不上）；
归属只在 `StatsAggregator` 一处判；营收只认 `SETTLED`，退房未结算按单数进"待结算"。

**权限与隔离**（V8）：`sys_user.property_id` 一列说完 —— 空 = 店长（全部门店 + 账号管理 + 建/删民宿），
非空 = 该民宿前台。**没有 role 列**（两列会组合出无法解释的状态）。判定收在 `common/AccessScope`：
- 房间域读写统一走 `RoomContext.of(roomId)` 顺手校验；
- **按 id 的读与改统一走各服务的 `require(id)`，校验写在 `require` 里面**（列表过滤做对了不等于按 id 安全）；
- 列表/报表入口用 `narrow(requestedPropertyId)` 求交，**越界抛 1003 而不是给空列表**；
- 操作日志带 `property_id` 并按它隔离（摘要里有房号和客人姓名）；
- 账号只有停用没有删除；**每个请求回读账号**，所以停用与改归属立即生效。

## 4. 十二轮审阅换来的四条习惯

1. **先核证据再动手**：用户拿另一个 AI 的截图来"审阅并修复"时，逐条对代码核实、给判定表，
   不盲信也不辩护。十二轮里**方向没有一条误报，但前提和数据会出错** —— 第十二轮说「`/users`
   只靠菜单隐藏」，实际服务端 `requireManager()` 早就在拒；上一轮把测试总数算成 164，实测 181。
   所以每条都要自己确认过才算数。
   （第十一条有一处机制说错了：它说"深夜跳过会让总数不是稳定的 181"。实测 `Tests run` 恒为 185，
   跳过只把 `Skipped` 从 0 变成 1 —— 结论方向对，量化口径要自己跑一遍才算。）
2. **"写进去的值"和"拿来说话的值"必须同源**。这一族缺陷反复出现：房型限制清空不生效
   （MyBatis-Plus 跳过 null）、`sale_type` 没写就被按钟点计费、清扫窗口挤短而日志照抄配置、
   部分更新回落成硬编码默认、清空归属升店长实际没清、接口返回 200 但库里 0 行、
   报错码被更靠前的可售性判断抢掉（3005 变 2003）。
   凡是"读一个配置去代表一件实际发生/落库的事"，都要问：实际值会不会不等于配置值。
3. **批量替换之后必须真跑一次**（渲染或测试）。两次回归都是这么来的：一次日历页整页空白，
   一次把存在性检查删掉了。
4. **"报出来的测试条数"本身也是一个要核验的值**。`grep -c @Test` 得到 25，surefire 只跑 24 ——
   因为第十一轮之前有一行的 `@Test` 粘在 `//` 注释尾部，被静默吞了九轮。
   所以：条数只认 surefire 输出，别认 grep、别认 README、别认上一轮的自己。
   同理，文档表格里的"补 N 条"要和实际 `@DisplayName` 逐行对得上，答辩时是会被一条条数的。

## 5. 还没做 / 有意留着的事

- **「开始时刻已过去」的口径没定死**（第 4 轮提出）：现在下单允许补录过去的时段、入住拒绝已结束的时段
  （必须改期或重开单）。要么明确"允许补录并记录 `actual_check_in`"写进论文，要么加时间下限。
  切换会牵动约 10 处测试夹具，**答辩前必须二选一**，别被问住。
- **权限只有"店长 / 前台"两档**，没有细粒度矩阵：前台可以改自己店的房型价格、清扫缓冲、房间状态。
  这是刻意的范围收束，答辩话术："隔离维度是门店，不是操作"。
- `PropertyService.list()` 的 N+1 **已收掉**（2026-10-30）：两条 `group by` 聚合取全表计数，固定 2 条 SQL
  替掉原来的 2N 条。`delete()` 里按 id 的计数保持原样 —— 它对一家店只判一次，本来就不是 N+1。
- **测试隔离**：Testcontainers 是 singleton 容器、跨类共享，没有 per-test 清库；
  用例靠 `System.nanoTime()` 造唯一名自保。`@EnableScheduling` 在测试里靠
  `bnb.hold.release-enabled=false` 关掉，新增定时任务要记得这个开关。
- 时间炸弹类用例：只剩一条。`OccupancyTruthIT` 的"清扫窗口被截断时日志写实际分钟数"用 `now()` 相对夹具，
  本地 21:00–03:59 会造出跨天钟点单，已用 `Assumptions` 主动跳过。**实测**：跳过时 `Tests run` 仍是 185，
  只是 `Skipped` 变 1、构建照样成功 —— 所以"185 全绿"这个说法在深夜要补一句。
  措辞逻辑由 `CheckOutLogNoteTest` 4 条纯单测确定覆盖，不随时钟。
  要彻底拔掉这颗雷得给 `BookingService.checkOut` 注入 `Clock`（多一个 Spring 上下文 + 一条测试专用接缝），
  当前判断不值得 —— 但如果以后再加 `now()` 相对用例，别再往这个方向走，直接注入 Clock。
- 前端：`StatsView` 打进主包 586KB（ECharts），构建有 chunk 体积告警，未做代码分割。
- 用户本人要做的：Mermaid 图渲染成 PNG、截演示图、写论文正文。
