三个虚线框是**不碰数据库、不读时钟的纯函数**：可售判断、算钱、报表聚合。
抽出来的理由在论文里可以统一讲：这些逻辑的难点是"边界口径"（缓冲算不算、取整取到哪、
凌晨算哪天），写在 SQL 或 service 里就必须连库造数据才能验证；做成纯函数后，
它们由 52 条表驱动用例覆盖（`PriceCalculatorTest` 34 + `StatsAggregatorTest` 18），
毫秒级跑完，改口径时立刻知道坏了什么。


图上要讲的三个设计点：

1. **`occupancy` 是唯一参与冲突检测的表**，`booking` 只是业务档案。所以历史订单在 `occupancy`
   里查不到 —— 退房即删行。由此推出一条铁律：**报表一律读 `booking`/`bill`，不读 `occupancy`**。
2. **`occupancy` 只有一对 `block_*` 参与判定**，业务时间 `start/end` 与它分开存。
   缓冲、提前入住、清扫窗口都只动 `block_*`，业务时间不动 —— 这样"客人看到的时间"和
   "系统挡房的时间"不会互相污染。
3. **`bill.detail_json` 是刻意的反范式**：账单要能回答"当时按什么价算的"，而规则和房型价都会改。
   把逐条明细与命中的规则名一起冻结下来，比加十张关联表便宜，也比只存一个总额诚实。

## 3. 时序图：下单（防超卖的核心路径）

```mermaid
sequenceDiagram
    autonumber
    participant F as 前台（浏览器）
    participant C as BookingController
    participant S as BookingService
    participant K as BookingKernel
    participant DB as MySQL

    F->>C: POST /api/bookings {requestId, roomId, start, end, saleType}
    C->>S: create(req)
    S->>DB: 查房间 / 房型 / 民宿（普通读，取缓冲与价格）
    Note over S,DB: ⚠ 这一步让 RR 的读视图提前建立<br/>所以后面的判定绝不能用普通读
    S->>S: SellPolicy.check()（策略：能不能卖）
    S->>K: createBooking(cmd)
    K->>DB: SELECT id FROM room WHERE id=? FOR UPDATE（房间行锁）
    K->>DB: SELECT ... WHERE request_id=? FOR UPDATE（幂等回放）
    K->>DB: SELECT o.id ... FOR UPDATE（重叠判定 = 当前读）
    alt 有重叠
        DB-->>K: 命中
        K-->>F: 3003 时段冲突
    else 无重叠
        K->>DB: INSERT booking
        K->>DB: INSERT occupancy(block=业务区间±缓冲)
        K-->>S: booking
        S->>DB: INSERT operation_log（谁在什么时候开了什么单）
        S-->>F: 200 + BookingVO
    end
```

要点：**锁只给互斥，当前读才给可见性**。第 6 步的 `FOR UPDATE` 是整份正确性的承重点 ——
`OversellWithoutLockIT` 把它换回普通 SELECT 之后，100 个并发请求全部成功（正常应为 10）。

## 4. 时序图：退房 → 清扫 → 结算

```mermaid
sequenceDiagram
    autonumber
    participant F as 前台
    participant K as BookingKernel
    participant B as BillingService
    participant H as 保洁
    participant DB as MySQL

    F->>K: POST /bookings/{id}/check-out
    K->>DB: 房间行锁 → 条件更新 IN_USE→CHECKED_OUT（写 actual_check_out）
    K->>DB: DELETE occupancy(kind=ROOM)
    K->>DB: INSERT occupancy(kind=CLEANING, [退房时刻, +clean_after])
    Note over DB: 房间仍未可售：没人点"清扫完成"之前，<br/>这行会从起点起持续挡房

    H->>K: POST /rooms/{id}/cleaning-done
    K->>DB: 房间行锁 → DELETE occupancy(kind=CLEANING)
    Note over DB: 此刻房间才真正恢复可售

    F->>B: POST /bookings/{id}/settle
    B->>DB: 房间行锁（与其它写路径同序，防 AB-BA 死锁）
    B->>B: PriceCalculator.price(区间, 覆盖时长, 粒度, 规则) ← 纯函数
    B->>DB: UPDATE booking SET status='SETTLED', amount=? WHERE id=? AND status='CHECKED_OUT'
    Note over B,DB: 影响行数 = 1 才算赢；赢家才有权插账单
    B->>DB: INSERT bill（含 detail_json 明细快照）
```

这条链上每个箭头都有对应测试，报告里最值得放的一句是：
**"可售"这个信号是保洁点出来的，不是时间到了自动变的** —— 这正是需求方要的闭环。

### 5.6 账号与按民宿隔离（论文 6.x 权限设计）

刻意不设 `role` 列 —— 两个字段能组合出"STAFF 但不绑店"这种没人能解释的状态，
